# Patch Clamp Acquisition Software — Architecture

## 1. Goal

A streamlined desktop GUI for episodic whole-cell patch-clamp recording from cultured cells or brain slices. The user patches a cell, clicks **Start**, and the software runs trials at a fixed inter-trial interval. Each trial issues a built-in seal-test pulse, then an optional optogenetic and/or current-injection stimulus, while continuously streaming the amplifier's scaled output. Trial-wise quality metrics (Rs, Ri, holding/Vrest) update live so the experimenter knows whether the recording is still good.

The target user is a novice — they should not have to think about DAQ channels, clock synchronization, or unit conversions. They think in mV, pA, ms, Hz.

## 2. Hardware

| Component             | Model                          | Role                                                                 |
|-----------------------|--------------------------------|----------------------------------------------------------------------|
| Amplifier             | Molecular Devices MultiClamp 700B | Patch amplifier. Mode (VC/IC) telegraphed to PC over USB.         |
| DAQ                   | NI PCIe-6323 (or similar X-series) | Hardware-timed analog I/O.                                       |
| LED driver            | Generic 0–5 V → LED current driver | Optogenetic stim. Brightness ∝ input voltage.                   |

### Channel map (proposed — needs confirmation)

| Direction | NIDAQ line | Target                                | Signal                              |
|-----------|-----------|---------------------------------------|-------------------------------------|
| AI        | `ai1`     | 700B SCALED OUTPUT                    | I (in VC) or V (in IC)              |
| AO        | `ao0`     | 700B EXT COMMAND                      | V (commands I in IC, V in VC)       |
| AO        | `ao2`     | LED driver analog in                  | 0–5 V brightness command            |

### Scaling / gain conventions

The user-stated values, written out explicitly so we can sanity-check before wiring them into code:

**Command path (DAQ AO → 700B EXT COMMAND):**
- Voltage clamp: 20 mV / V  →  to command −5 mV, write −0.25 V
- Current clamp: 400 pA / V →  to command −100 pA, write −0.25 V

**Scaled-output path (700B SCALED OUTPUT → DAQ AI):**
- Voltage clamp: 1000 pA / V (i.e. 1 V at AI = 1 nA at cell)
- Current clamp: 20 mV per mV at cell (i.e. 1 V at AI = 50 mV at cell)

> ⚠ The 700B's scaled-output gain is **user-configurable on the front panel and reported via telegraph**. Hard-coding it is fragile. We should read it from the telegraph rather than trust a constant. (See Q1 in `tasks.md`.)

### Mode telegraph

The MultiClamp Commander software (Windows-only) exposes the amplifier's state over a named-pipe / shared-memory IPC. The standard interface is the **MCC Commander API** (`AxMultiClampMsg.dll`) or community Python wrappers (`pymcc`, `pyMCC`, `pyclamp`). It reports:
- Mode (VC / IC / I=0)
- Primary output gain & units
- Holding command
- Filter, etc.

This is **Windows-only**. See §9.

## 3. Trial structure

Default trial length: 1.0 s. User-editable. Sample rate: 20 kHz (proposed default).

```
 t=0       50ms          150ms         200ms        300ms                   end
 |---------|-------------|-------------|------------|-----------------------|
   pre-      seal-test     post-         pause        stimulus window
   baseline  step          baseline                   (opto AO2 and/or
   (50 ms)   (100 ms)      (50 ms)      (100 ms)      command-AO0 train)
```

- **Seal-test step:** −5 mV (VC) or −100 pA (IC). Fixed by default, editable in an "advanced" panel.
- **Stimulus window:** anything from t = 300 ms to end of trial is available for opto and/or command-side pulse trains.
- **Inter-trial interval:** user-editable; during ITI no AO is driven (held at 0 V / holding command).

Per-trial timing is generated by the DAQ's onboard sample clock, not Python. AO and AI tasks share the same sample clock and are started with a single trigger so they are sample-aligned.

## 4. Software stack

| Layer            | Tool                                                       | Rationale                                                        |
|------------------|------------------------------------------------------------|------------------------------------------------------------------|
| Language         | MATLAB R2023a+ (R2024a preferred)                          | User preference; mature instrument-control ecosystem.            |
| DAQ              | Data Acquisition Toolbox (`daq` interface, session-based)  | Hardware-timed finite AO/AI, shared sample clock, start trigger. |
| 700B telegraph   | Molecular Devices `AxMultiClampMsg.dll` via `NET.addAssembly` (or `loadlibrary`) | Mode + gain readback.                              |
| GUI              | Programmatic `uifigure` + `uipanel` (NOT App Designer `.mlapp`) | Plain `.m` files diff cleanly — required for multi-agent work. |
| Plots            | `uiaxes` with manual data updates                          | Native, no extra deps; fast enough at 20 kHz / 1 s trials.       |
| Numerics         | Base MATLAB + Signal Processing Toolbox (if available)     | `polyfit`, `findpeaks`, basic filtering.                         |
| Storage          | HDF5 via `matfile('-v7.3')` or direct `h5create`/`h5write`  | One file per session, one group per trial.                       |
| Config           | `struct` validated by a `ConfigSchema.validate()` helper, serialized to JSON | Human-editable, round-trips through `jsonencode`. |
| Tests            | `matlab.unittest` framework + `FakeBackend`                | Allows headless development on macOS.                            |

### Required MATLAB toolboxes
- **Data Acquisition Toolbox** (for NI-DAQmx access on the rig PC).
- **Instrument Control Toolbox** — *not* required for the 700B (we use the MCC DLL), kept off the dependency list.
- **Signal Processing Toolbox** — nice-to-have for filtering / fitting; the code should degrade gracefully if absent (Rs is peak-only and doesn't strictly need it).

### MATLAB-specific design rules
- **One class per file** (`classdef Foo` in `Foo.m`). This is enforced by MATLAB and is the basis for the multi-agent file-ownership model — see `tasks.md`.
- **Use `+package` folders** to namespace. All code lives under `+patchclamp/...`. Call sites use `patchclamp.hardware.FakeBackend()` etc.
- **No `App Designer .mlapp` files.** They are partially binary and cannot be merged across parallel agent workstreams. The GUI is built programmatically with `uifigure`.
- **Public APIs use `arguments` blocks** for argument validation. Cell-unit values are validated at the boundary.

## 6. Concurrency model

MATLAB is single-threaded for user code. We use the following pattern:

1. **Main thread runs the `uifigure` event loop.** Buttons, dropdowns, plots all live here.
2. **`ExperimentRunner` is event-driven, not threaded.** Per trial it (a) builds the AO waveforms, (b) hands them to the DAQ backend, (c) calls `start(daq, "continuous"=false)` which is hardware-timed and non-blocking from MATLAB's perspective, (d) registers a `DataAvailable` listener that fires when the AI buffer fills, (e) on the listener: analyzes, fires a `TrialFinished` event, schedules the next trial via a one-shot `timer` for the ITI.
3. **Telegraph polling** is a separate `timer` object (~5 Hz period) that calls into the MCC DLL and fires `ModeChanged` / `GainChanged` events when values change. The GUI listens and updates the mode label + unit labels.

DAQ timing is hardware-clocked on the PCIe-6323 — MATLAB never controls sample-to-sample timing. The AO and AI subsystems share the onboard sample clock and start on the same trigger, so they are sample-aligned regardless of MATLAB's responsiveness.

All cross-component communication uses MATLAB `event`/`notify` (handle classes inherit from `handle` and declare `events`). No globals.

## 7. Data model

MATLAB `struct`s with a centrally-defined schema (validated by `+config/TrialConfig.validate()`). Field names are fixed; any code that produces or consumes these structs must use these exact names.

```matlab
% Trial config (user-editable, persisted to JSON)
trialConfig = struct( ...
    'trialLengthSec',  1.0, ...
    'sampleRateHz',    20000, ...
    'itiSec',          1.0, ...
    'sealTest',        sealTestStruct, ...
    'opto',            pulseTrainStruct,  ...   % or [] if disabled
    'commandStim',     pulseTrainStruct,  ...   % or [] if disabled
    'mode',            "VC" );                  % mirrored from telegraph

% Parametric pulse train
pulseTrain = struct( ...
    'pulseDurationMs', 5.0, ...
    'amplitude',       50.0, ...   % units depend on context — see Q3
    'frequencyHz',     20.0, ...
    'nPulses',         10 );

% Single-trial result (emitted by ExperimentRunner)
trialResult = struct( ...
    'index',          uint32,  ...
    'timestamp',      datetime, ...
    'aiCellUnits',    double,  ...   % scaled output, already converted (mV or pA)
    'aoCommandCellUnits', double, ... % what we sent, in cell units
    'aoLedVolts',     double,  ...
    'rsMohm',         double,  ...   % NaN in IC
    'riMohm',         double,  ...
    'holding',        double,  ...   % pA (VC) or mV (IC)
    'mode',           "VC",    ...
    'gainSnapshot',   gainStruct );  % gain as reported by telegraph at trial start
```

Storage: one HDF5 file per session via `h5create`/`h5write`. Layout:
```
/meta/
  config              (JSON string)
  startTimestamp
  cellId
/trials/000000/
  aiCellUnits         (N×1 double)
  aoCommandCellUnits  (N×1 double)
  aoLedVolts          (N×1 double)
  rsMohm, riMohm, holding, mode, gainSnapshot (attrs)
/trials/000001/...
```

## 8. Analysis (seal-test epoch)

All measurements operate on the first 200 ms of each trial, where the seal-test step lives.

- **Holding (VC) / Vrest (IC):** mean of first 10 samples (i.e. first 0.5 ms at 20 kHz). User-noted; trivial.
- **Input resistance (Ri):** mean of the steady-state window (e.g. last 30 ms of the 100 ms step) minus baseline mean, divided by step amplitude. Excludes the fast capacitive transients at onset and offset.
- **Series resistance (Rs, VC only):** from the peak of the capacitive transient at step onset, `Rs = ΔV / I_peak`. Optionally cross-check via single-exponential decay fit. The choice between peak-only and fit-based is worth a brief discussion (see Q4).

All conversions to MΩ live in one place (`analysis/units.py`) so we can audit them.

## 9. Platform reality check

MATLAB runs on macOS, but **Data Acquisition Toolbox NI support and the MultiClamp Commander DLL are Windows-only**. Dev happens on Mac; integration on the rig PC.

Plan:
- `FakeBackend` and `FakeTelegraph` exist from day 1 and synthesize plausible traces (RC step response + injected stimulus + Gaussian noise) with programmable Rs/Ri/Cm/Vrest. All Mac-side development runs against them.
- Real hardware code (`NidaqBackend`, `MccTelegraph`) is gated by `ispc()` checks at construction time. The classes exist on Mac but throw a clear error if instantiated there; nothing imports a Windows-only DLL at file-load time.
- The backend is chosen via a single switch in `runApp.m` (or auto-detected: `ispc() && hasDataAcquisitionToolbox()` → real, else fake).

## 10. Out of scope (for v1)

- Arbitrary waveform stimuli (mentioned in spec §9 — "more complicated continuous function"). v1 ships parametric pulse trains only.
- Online spike detection or event extraction.
- Multi-channel / multi-electrode recording.
- Post-hoc analysis GUI (HDF5 export is enough; users analyze offline).
- Automatic seal/break-in detection.
